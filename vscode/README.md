# Salvo for VS Code

Syntax highlighting and language-server support (diagnostics, hover,
go-to-definition) for the Salvo programming language (see `README.md` and
`docs/language/` at the repository root), and for its **platform templates**.
The language server is the `salvo` compiler itself, started as `salvo lsp` over
stdio.

## Platform templates

A platform template — `platform/<module>.sv.kt` or `.sv.rs` — is Kotlin or Rust
in which every `` `…` `` marker is Salvo (see "Platform templates" in
`docs/language/Backends.md`). The extension registers two languages for them,
**Salvo template (Kotlin)** (`salvo-kotlin`, `*.sv.kt`) and **Salvo template
(Rust)** (`salvo-rust`, `*.sv.rs`):

- **Highlighting**: the file highlights as its host language, each marker as
  Salvo, and `@name` / `@{…}` inside a marker as the host again. Strings and
  comments stay host text, and a doubled backtick is the host's own — so
  Kotlin's ```` ``in`` ```` stays an escaped identifier.
- **Language server**: the template's diagnostics are reported at its own lines;
  hover and go-to-definition work inside markers (a declaring marker's header,
  `` `fn shout(g: Greeting) -> Str` ``, answers as the `.sv` declaration does),
  and nothing answers in host text. An unsaved edit is analysed as it stands,
  and a template finds its project the way a `.sv` file does.

The host half comes from the host language's own grammar: VS Code ships Rust's,
but **not Kotlin's** — install a Kotlin extension providing `source.kotlin` (for
example `fwcd.kotlin`) for the Kotlin text around the markers to be coloured.
Without it the markers still highlight.

If another extension claims `*.kt` or `*.rs` files in a way that wins over
`.sv.kt` / `.sv.rs`, associate them explicitly:

```jsonc
{ "files.associations": { "*.sv.kt": "salvo-kotlin", "*.sv.rs": "salvo-rust" } }
```

## Build and install

```bash
cd vscode
npm install
npm run compile
```

Then either launch an Extension Development Host (open `vscode/` in VS Code
and press F5), or package and install it:

```bash
npx @vscode/vsce package   # produces salvo-vscode-<version>.vsix
code --install-extension salvo-vscode-*.vsix
```

## Pointing at your salvo binary

The extension spawns the binary named by the `salvo.serverPath` setting
(default: `salvo` on PATH). While hacking on the compiler, point it at the
build output — relative paths resolve against the workspace folder:

```jsonc
// .vscode/settings.json in the salvo-lang repo
{
  "salvo.serverPath": "target/debug/salvo",
  "salvo.backend": "" // or "kotlin" / "rust" to include that backend's define files
}
```

After `cargo build`, run **Salvo: Restart Language Server** from the command
palette to pick up the new binary (changing either setting also restarts it
automatically).

## Regenerating the grammars

`syntaxes/salvo.tmLanguage.json` is generated by the compiler so keyword
highlighting can never drift from the lexer, and so are the two template
grammars, so their marker rules follow the template scanner:

```bash
cargo run -- lang tm-grammar --out vscode/syntaxes/salvo.tmLanguage.json
cargo run -- lang tm-grammar --template kotlin --out vscode/syntaxes/salvo-kotlin.tmLanguage.json
cargo run -- lang tm-grammar --template rust --out vscode/syntaxes/salvo-rust.tmLanguage.json
```

Tests in `salvo-cli` (`vscode_extension_grammar_is_up_to_date`,
`vscode_template_grammars_are_up_to_date`) fail if a checked-in file is stale,
and `vscode_extension_registers_the_template_languages` checks that
`package.json` and the client register the template languages under the
generated scopes.

## Note on `.sv`

Salvo uses the `.sv` extension, which SystemVerilog extensions also claim.
If both are installed, pick the language per-file ("Change Language Mode")
or associate it per-workspace:

```jsonc
{ "files.associations": { "*.sv": "salvo" } }
```
